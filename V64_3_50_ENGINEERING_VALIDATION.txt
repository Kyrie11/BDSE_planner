V64.3.50 EAF-ICER-SIOR — live-selection eligibility / cohort-semantics repair validation

Trigger
-------
After the earlier event-state and state-local action-slot repairs, native paired
collection progressed through the first two V49 discovery-cohort scenes and then
stopped on token 04e294754b4d56a6 with:

  expected exactly one first proposal marker in both arms, got 0/0

The strict selected-outcome diagnostic stream was present.  Therefore 0/0 did
not mean the marker logger failed: neither CONTROL nor TREATMENT emitted a live
RSMR direct proposal anywhere in that native closed-loop scenario.

Root cause
----------
V50 still conflated two different populations:

  1) V49 offline discovery cohort: 502 TRAIN scenes selected by offline V49
     instrumentation; and
  2) V50 live intervention cohort: native closed-loop states in which the frozen
     RSMR policy actually emits a direct proposal, so a one-shot selected-action
     treatment is defined.

Offline membership does not guarantee live treatment eligibility.  Treating a
symmetric no-proposal replay as an engineering exception makes the experiment
impossible; treating it as a negative SIOR label would be scientifically wrong
because no treatment was available or executed.

Repair
------
- Keep all 502 V49 scenes as the frozen offline discovery/transport cohort.
- Every token is still replayed in paired CONTROL/TREATMENT native nuPlan runs.
- If both arms reach the same first live RSMR proposal event, keep all prior
  same-state identity/QPE/one-shot invariants and label the paired selected
  outcome (`pair_status=eligible_intervened`).
- If neither arm ever emits a proposal, record
  `pair_status=no_live_proposal`, `live_intervention_eligible=0`; prove whole-run
  CONTROL/TREATMENT deployed action + trajectory-fingerprint equality, zero
  proposal/intervention counters, and official score/hard-metric equivalence.
  Do NOT create a safe_benefit/nonbenefit label and exclude the row from SIOR
  fit/calibration/test.
- Exactly-one-arm proposal, malformed marker state, pre-treatment divergence,
  proposal/fingerprint/QPE mismatch, or multiple treatment execution remains an
  ENGINEERING STOP.
- The paired CSV has a new locked protocol version
  `v50-live-selected-event-cohort-v1`; both collector resume and the fit tool
  reject older/missing versions so old V50 rows cannot be mixed silently.
- V49 OBS comparator is reconstructed on the full frozen 502 offline selected
  population for each fold, not the live-eligible subset, then evaluated on the
  same live Q/P/E test states and closed-loop labels as SIOR.  This prevents
  live-eligibility leakage into the baseline fitting distribution.

Scientific population-support discipline
----------------------------------------
No live-eligibility-rate threshold was invented after observing this failure.
Instead, fitting is allowed only if the live selected-event population satisfies
the already-frozen V48/V49 estimator support requirements:

  - every nested fit split: >=32 safe-benefit and >=32 nonbenefit events;
  - every calibration fold: >=16 safe-benefit events;
  - every held-out fold: both classes present;
  - final fit/calibration: the same inherited minima.

If support fails, V50 writes the 502-scene cohort-transport audit and SCIENTIFIC
STOPs before risk fitting/fresh evaluation.  It must not relabel no-proposal
scenes, lower minima, change loss/threshold, or expand the risk head.

Interpretation / protocol status
--------------------------------
This is not merely a missing-marker engineering fix.  It corrects an experiment-
unit/estimand flaw: V50 SIOR is an outcome model conditional on a real live
selection event.  The 502-scene V49 population remains useful as a frozen
offline discovery cohort and separately measures offline->native selection
transport.  The core SIOR hypothesis (replace offline pseudo-intervention labels
with native paired selected-outcome evidence) is unchanged, but any paper claim
must distinguish offline discovery coverage from conditional live selected-event
outcome identification.

The repair was designed from proposal-eligibility/diagnostic information only;
no paired score or hard-safety outcome from the failing 0/0 token was provided to
or inspected by this analysis.

V64.3.50 performance-only batched paired-collection execution repair
--------------------------------------------------------------------
Trigger: server collection progressed without semantic failure but single-scenario
throughput was impractically slow. Code audit found 502 sequential pair waves and
1004 fresh Python/Hydra/nuPlan process launches. The existing per-process model
cache therefore had almost no opportunity to amortize checkpoint/model loading,
and every child repeatedly received the four full TRAIN DB directories.

Repair (scientific protocol unchanged):
- `collection_protocol_version` remains `v50-live-selected-event-cohort-v1`.
- New execution provenance only: `collection_engine_version=v50-batched-nuplan-v1`.
- Default `V50_BATCH_SIZE=16`: one CONTROL and one TREATMENT process per token
  batch, concurrent on GPU0/GPU1; `worker.max_workers=1` keeps scenarios serial
  within each arm process.
- Official nuPlan per-scenario metric rows are joined by exact native scenario
  token and every token still runs the same `_validate_pair()` independently.
- Process-global read-only model sharing is now amortized across batch scenarios.
- Build an outcome-blind 502-token -> exact native `.db` file index once; each
  batch passes only relevant DB files. Exact-index failure falls back to the old
  configured DB inputs and never changes the cohort.
- V50 collection writes only the selected-outcome diagnostic certificate rather
  than the unused full planner diagnostic tree on every tick.
- Resume rejects legacy engines and a different requested batch size; batch size
  is execution provenance and must remain frozen for one collection.
- Per-tick replanning, native reactive simulation, CONTROL/TREATMENT policies,
  one-shot intervention, official score/hard metrics, Q/P/E, labels, SIOR model,
  calibration and all scientific gates remain unchanged.
